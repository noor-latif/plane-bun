## First: a small measurement contract

Before optimizing, capture one fixed production-mode stack with synthetic data. Use the same host, resource limits, dataset, worker counts, and workload on both sides. At launch, obtain a single bounded execution approval covering the host, model calls, concurrency, and exact classes of installs/builds/tests/service starts/benchmarks. Continue inside that scope without repeated permission prompts; ask again only when scope changes. Host selection is an execution-time decision: neither nixlab availability nor permission for heavy laptop work is assumed.

**P0 is measurement, not an optimization.** Exploratory B/C and C1 measurements exist; M13 withdraws their completion/KEEP claims. M15 adds three failed constrained reference trials with repaired checks, not a usable equal-work control. Resolve the reference failures before candidate comparisons. Rank subsequent candidates from measured service cost and implementation effort, but do not interpret lower memory during failed work as a saving. Report CPU, browser memory, image size, and maintainability separately.

1. For P0, use cgroup v2 `memory.current` in bytes per experiment container, sampled on a fixed cadence with timestamps and container/service identity. Record collector/version, cgroup membership, and included services. Report the sum of each sampling round and its observed peak; do not sum each service's independent peak. This is container-accounted memory including cache, not PSS or an exact host physical-memory total. Missing samples invalidate the comparison; never replace them with zero. If the approved host lacks this instrument, choose and document another container metric before baseline collection.
2. Keep historical process-tree PSS and new container measurements in separate series. Record CPU time, completed operations, p95 latency, errors, effective worker concurrency, active database connections, and queue backlog. Baseline and candidate use the same instrument on the same host; historical laptop numbers are context, not the new control.
3. Exercise board reads, issue updates, page edits, upload/download, real queued background work, and collaboration reconnects. Record durable outcomes, not just HTTP status codes. Seeding is setup: `create_dummy_data` calls its task function directly and requires an existing user; its success text is not evidence of queued work. Before P0, name an actual application dispatch path, task mix, synthetic inputs, and durable completion checks.
4. Alternate baseline/candidate order with at least three samples per condition for short comparisons. Restore equivalent data/cache state and declare warm-up, sample duration, offered load, and recovery window. Run only one measured experiment at a time on an otherwise quiescent approved host; pause competing builds/tests and local agent workloads. Keep development and production results separate.
5. Before candidate measurements, write numerical gates for minimum useful memory saving, maximum p95/queue-delay regression, and backlog recovery time, using baseline variability and the target workload. Require unchanged durable outcomes and no new errors/data loss. A worker comparison holds arrival rate and task mix fixed, including a burst; a self-throttling producer hides lost capacity. Gains inside observed noise are inconclusive, not wins.
6. Every result names the question, single changed variable, exact revisions/configuration, raw evidence, completed-work checks, limitations, and keep/reject/inconclusive verdict. For lazy imports, separate cold idle, first-use latency/peak, and post-use steady state; module retention can erase the cold-idle saving.

Use lightweight outcome checks for this discovery pass. Do not build a comprehensive test suite first. A benchmark that drops jobs, skips writes, weakens validation, or serves less useful work is not an optimization win.

### Compatibility vocabulary and feature contract

- **D: drop-in candidate.** The existing protocol or file format is supported; configuration, persistence, extension behavior, and rollback still need proving.
- **B: bounded migration.** A specific interface or integration changes; callers and behavior to preserve are identified.
- **A: architectural migration.** Multiple domains, shared-state guarantees, or stored formats change. This is not a package-name substitution.
- **Keep:** no evidence that replacing the incumbent beats reducing its actual workload.

Separate two outcomes: **same-feature lean deployment** and **lean-core redesign**. For the latter, state retained and removed capabilities explicitly and compare the same retained workload on both sides. Candidate core: authentication and workspace/project visibility; work items and their views; pages and collaborative editing; attachments; and the API/background operations supporting them. This research does not authorize deleting other features.

### Six experiments worth doing before a broad rewrite

1. **Remove optional PDF and browser UI from Live's baseline import graph.** First lazy-load the PDF implementation without deleting its endpoint. Separately introduce schema-only server extensions, starting with the proven emoji-suggestion chain. Affected surface: Live controller/service imports, editor server codec extensions, export packaging/assets, and existing document conversion callers. Measure cold idle, first use, and post-use steady-state memory while checking representative document conversions and persisted schemas. A cold-idle-only win is a startup result, not proof of lower long-running deployment memory.
2. **Hocuspocus 4, then native Bun transport.** Upgrade the collaboration library on the existing host first. Map `lib/auth.ts`, `extensions/database.ts`, `extensions/redis.ts`, `extensions/title-sync.ts`, `extensions/force-close-handler.ts`, and `lib/drain-server.ts` against the breaking-hook guide. `context`/`lastContext`, web `Headers`, transaction origins, manual message/close forwarding, and drain internals matter. Only after parity, replace the HTTP/WebSocket shell. Existing `apps/live/tests/integration/hocuspocus-v3.test.ts` supplies relevant wire/document scenarios; running or adapting it is a later approved execution step, not evidence already obtained here.
3. **Remove RabbitMQ while preserving the task implementation.** First prove Redis transport on the existing topology with a separate logical broker database and explicit persistence, eviction, and failure policies; then remove broker services/dependencies/templates. `clear_cache` calls Django `cache.clear()`, so verify the actual cache backend/database remains separate from queued jobs. Logical databases do not isolate instance-wide memory pressure or eviction; queued jobs must not be exposed to cache eviction, and memory-limit write failures must remain visible. Measure additional Valkey memory and contention, real job outcomes, retries, restart recovery, and net stack saving. The inspected webhook decorator does not establish a retry beyond one hour: Celery's default retry-backoff ceiling is 600 seconds [S15]. Do not prescribe an arbitrary 12-hour visibility timeout.
4. **Reduce resident concurrency and duplicate static servers.** Bound prefork first; try threads/solo separately if the task mix permits. Consolidate gateway asset serving as another independent change. Embedded Celery beat normally uses a separate process: `worker -B` is not proof of fewer interpreters or lower RSS. Process count, completed jobs, and queue delay decide.
5. **Try in-family native/memory improvements.** Compare Valkey 9.1 with the actual key mix; compare TypeScript 7 CLI checking with current diagnostics and generated types. These optimize different budgets. Valkey's quoted 17-44% is vendor-measured per-key overhead against 9.0 at millions of keys, not whole-server RSS or a Plane prediction. TypeScript's published gains concern builds, not deployed Plane RAM.
6. **Prove one browser import/state boundary.** Compare a Lite editor subpath or a non-default issue-layout lazy import in one route, including first-use latency and chunk duplication. Investigate one state-owner consolidation separately. Do not replace MobX or the whole editor just to make the dependency list shorter.

Dependency-deletion leads include the HTTP-only Channels wrapper, unused result-backend declarations, and frontend declarations with no source/config usage found (`comlink`, `emoji-picker-react`, `react-fast-compare`, `react-is`). Recheck dynamic/peer/extension consumers before removing them. These can reduce installation/artifact weight; unimported packages do not automatically explain resident RAM.

**Backend-specific probes:** compare a small Django/psycopg pool with the current per-request connection behavior, using the same ASGI server and workload; record connection churn, active/idle connections, memory, and p95. Keep only if the bounded pool improves the actual budget. Separately inspect one search or pagination query with `EXPLAIN (ANALYZE, BUFFERS)` on synthetic data; match the generated expression before trying an index. Neither probe requires replacing Django/DRF. A normal-GIL Python version trial is separate from both; current Psycopg free-threading support remains experimental according to its maintainers [S18].

### Two end states, with different refactor costs

**Same-feature lean deployment:** shared static gateway; unchanged Django models/API behind a smaller serving stack if it wins; controlled Celery concurrency; PostgreSQL; Valkey also carrying the task broker if its semantics pass; existing S3 contracts; Hocuspocus 4/Bun; separately decide whether Space can share that Bun host. Preserve public APIs, document formats, permission revocation, scheduled jobs, and exports. This is the preferred first path.

**Lean-core single-instance design:** keep Django and PostgreSQL, replace Celery/RabbitMQ/beat with PostgreSQL-backed jobs, and consider removing Valkey only after replacing every shared-cache/authentication-counter/notification-lock/Live pubsub consumer. Sessions already use PostgreSQL. Live would need local document coordination and an authenticated internal event path for title sync and forced disconnects. Retained product features may include collaborative pages and attachments; distributed Live scaling, isolation, and recovery behavior change. Task decorators/dispatch sites, schedules, retries, API-to-Live events, and caches form the migration surface. This is an A-class refactor, not several configuration toggles.

Do not confuse a single container with this second design. Colocating the existing programs leaves their interpreters, pools, and state alive.

## Easier refactoring: one representative feature

Use a real feature change as the maintainability experiment, not a repo-wide reorganization.

- Map its callers, state, policy decisions, persistence, and side effects. Shared and application-specific stores are not automatically duplicates.
- Pick one rule with multiple equivalent owners or one pass-through layer that adds no useful behavior. Preserve intentional differences.
- Give the rule one small interface within the existing architecture. Keep transactions, validation, authorization, and job dispatch explicit; introduce no generic repository/service framework.
- Migrate all affected callers. `packages/codemods` already supplies jscodeshift and a Vitest convention for repetitive transformations; existing transforms do not implement this migration automatically.
- Measure improvement by the places a representative change must touch and the concepts a caller must understand. Count deleted code/dependencies as supporting evidence, not the goal.
- Keep mechanical relocation separate from behavior/performance changes. Finish each cutover by removing obsolete paths rather than retaining permanent compatibility wrappers.

## Explicitly parked

- Default cutovers to a new backend, database, state library, or editor/collaboration protocol. They are researched above, not authorized for implementation; bounded experiments and lean-core designs require explicit scope choices before a feature or compatibility contract is removed.
- Disabling features, permissions, validation, persistence, retries, or error reporting to improve benchmark numbers.
- Moving Web/Admin production serving to Bun: they are already static.
- Merging application processes or introducing caching/pooling/adapter layers without a demonstrated cost. The scoped gateway and shared-Bun-host experiments above are candidates, not presumed winners.
- A broad safety audit or comprehensive regression-suite build during this proof pass.
